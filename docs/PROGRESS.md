## Phase 3 — done

**Goal:** more indexable surface against method-level queries, then dev tools,
then make the data itself citable.

- [x] **Method pages** — `/charges/upi/`, `/credit-card/`, `/debit-card/`,
      `/netbanking/`, `/international/`. Each ranks all 8 providers on one
      method with the GST-inclusive rate and any annual fee, which is a cut of
      the data that appears nowhere else on the site.
      Sitemap 58 → 63.
- [x] **Interactive calculator** — volume and average-transaction sliders on a
      log scale, five payment-mix sliders that self-normalise so they never
      have to add up to 100. Two-pane sticky layout from 1280px.
      Initial state *is* the defaults, so Next server-renders the full result
      table (9 tables, 8 breakdowns, real figures) before any JS runs; a
      crawler sees the numbers and hydration makes them live. `check-ssr`
      asserts this, because a calculator that only renders after hydration is
      invisible to search.
- [x] **Dev tools** — `/tools/` plus four tools. Each page server-renders a
      reference table (the formulas, the IIN ranges, the working-day rules, the
      bank codes) and puts the interactive part on top, because a tool page
      whose only content is a form has nothing to index and nothing to say to
      someone who wanted an answer rather than a calculator.
      Sitemap 63 → 68.
  - **Webhook signature verifier.** Razorpay, Cashfree, PayU and PhonePe,
    transcribed from their own docs. Hashing is `crypto.subtle` in the browser:
    a webhook secret is a live credential, and hashing it server-side would
    make us a place where secrets go. Verified against the RFC 4231 HMAC-SHA256
    vector in a real browser, and against `node:crypto` for SHA-512.
    The page shows **the assembled signing string** with the pipes highlighted,
    which no provider's documentation prints and which is where the bug
    actually is.
  - **Card BIN checker.** Network from published prefix ranges, longest-prefix
    wins so RuPay's `652` beats Discover's `65`, plus Luhn and a cross-provider
    MDR table. Names the issuing bank for 1,138 Indian bank IINs and says
    plainly that Visa and Mastercard issuers are not knowable from published
    data — which is the thing every commercial BIN site gets wrong.
  - **Settlement date calculator.** T+n in bank working days, skipping Sundays
    and second and fourth Saturdays. Shows the day-by-day trail with a reason
    for each skip. Ships no festival calendar on purpose (see below).
  - **IFSC checker.** Structure offline from 242 bank codes, branch detail via
    our own cached endpoint. Leads with the fact that an IFSC has **no check
    digit**, so a mistyped branch code is another well-formed IFSC.

**Bank dataset.** `data/seed/banks.json` — 242 IFSC bank codes and 1,138 bank
IINs, from release v2.0.62 of the MIT-licensed `razorpay/ifsc` dataset.
Committed, and regenerated by `scripts/build-bank-seed.mjs` so the provenance
of every row is reproducible rather than a blob pasted in once. One dataset
serves two tools.

**Why there is no festival holiday calendar.** Indian bank holidays are
declared per state under the Negotiable Instruments Act and the festival dates
move every year. A built-in list would be wrong for most users on day one and
wrong for everyone within a year, while looking as authoritative as the parts
that are right. The tool computes what is deterministic and takes the rest as
input.

**Provider documentation contradicts itself, twice.** Both are published rather
than quietly resolved:
- PayU's hash page says "15 delimiters in total"; its own sample code in five
  languages produces 16. We follow the sample code, because that is what
  merchants ship, and the page says so.
- Razorpay's pricing page says settlement is T+1; their settlement docs and
  FAQ both say the standard cycle is T+2 working days. The settlement tool
  shows both with links. **The seed still holds T+1** and `/charges/razorpay/`
  still shows it, because the pricing page is the rate card we cite — see
  Known gaps.

**Client-bundle fix, worth 30 KB on every interactive page.** Zod was reaching
the browser by two separate routes, both of them a barrel re-export:

1. `@/common/ui` re-exports `Breadcrumbs` → `@/common/config` → zod, so any
   client component importing the barrel shipped a schema validator in order to
   render a text input. The tool components import `@/common/ui/field` directly
   instead: tool pages 220 KB → **190 KB gzipped**.
2. `@/modules/pricing/client` re-exported `METHOD_LABEL` from
   `pricing.schema.ts`, which imports zod. Zod builds its schema objects at
   module scope, so no bundler can shake them out — the calculator downloaded
   118 KB of validator to print the word "UPI". The allowed values now live in
   `domain/pricing.constants.ts`, which **imports nothing**; the schema builds
   its enums from those arrays, so there is still one source of truth per value.
   `client.ts` takes values from the constants and types from the schema via
   `export type`, which the compiler erases outright. `/calculator` and its six
   scenario pages went 210.6 KB → **180.6 KB gzipped**, under the 200 KB budget
   with 19 KB of headroom. `/compare` loads an identical chunk set and measures
   the same 180.6 KB.

Measured the way a browser experiences it: every `<script src>` in the emitted
HTML, gzipped. All 70 prerendered routes now share 12 client chunks and **not
one contains zod or `node:fs`**. The three largest are React and the Next
runtime, which is the floor.

**And a guard, because this leak has now happened twice.** Both times the cause
was a barrel re-export, both times it was found by measuring by hand, and
neither time could anything have failed a build. `scripts/check-bundle.mjs`
(`npm run check:bundle`) reads the production build, collects every
`<script src>` from each prerendered page, and asserts two things per route:

- no chunk contains a **server-only module** — zod, `node:fs`, drizzle, or a
  serialised seed record. Each marker is a string that survives minification
  (`ZodError`, not `"zod"`), and each failure names the offending chunk and the
  fix.
- the route's total gzipped JS is within the **200 KB budget**. The React + Next
  floor is ~177 KB, so there is only ~23 KB of room — tight on purpose, since
  the leak it exists to catch was 30 KB.

It reads the build rather than a running server, unlike check-ssr, because dev
chunks are unminified, carry the whole module graph under readable names, and
are never what ships.

**The guard was verified by reintroducing the bug**, not by watching it pass: a
single `export { METHOD_LABEL } from './pricing.schema'` put it back, and
check-bundle failed with **102 failures across 51 of the 70 routes** — naming
the chunk, the route and the remedy on each. That run also settled a question
worth recording: how far zod spreads is decided by how the bundler groups
modules, not by which page imports it, so **"it only costs the calculator" was
never a safe assumption**. Both axes fired independently — the marker check and
the budget check — so a future leak small enough to stay under budget still
fails the build.

**Nav regression, caught and fixed.** A seventh nav item pushed the theme
toggle 39 px past the viewport at exactly 768 px, giving every page a
horizontal scrollbar. `md:flex-wrap` on the nav panel; verified at 375, 768,
1024 and 1440.

**API routes.** `/api/bin/[iin]` serves the committed seed and **refuses
anything longer than six digits**, so a full card number cannot reach our logs
even if a caller sends one. `/api/ifsc/[code]` proxies the public IFSC API,
validating against an anchored pattern before the code reaches a URL and
mapping the response field by field rather than passing a third-party object
through to the browser.
- [x] **Public dataset** — `/data/` plus `pricing.json` and `pricing.csv`.
      Sitemap 68 → 69.

**Why give away the thing we rank for.** A compilation nobody can cite is a
compilation nobody links to. An assistant answering "what does Razorpay charge
for UPI" needs a figure it can attribute; a developer pricing a checkout wants a
file, not a table to retype. Publishing under **CC BY 4.0** makes attribution a
licence condition rather than a hope, and the licence URL pins the version
because Google's guidance marks the version-less form as not recommended.

What the licence actually covers is stated on the page rather than implied: a
rate of 2% is a fact and facts are nobody's property. Ours is the compilation —
which providers, which methods, the GST-inclusive figure worked out for each,
and the verification date and source pinned to every row.

**Version is derived, not stamped.** `version` is the newest `verifiedAt` in the
data, never a build timestamp. A timestamp would change the bytes on every
deploy: every consumer's cache would miss, every diff would be noise, and nobody
could tell a redeploy from a repricing. Providers are sorted by slug for the same
reason — seed file order must not move the output. A test asserts both.

**Two shapes, because there are two readers.** JSON keeps the full structure
(fixed costs, settlement cycles, promos, recorded rate changes, third-party
source attributions). CSV flattens to one row per provider and method — 63 rows,
21 columns — which is what a spreadsheet wants. Escaping is RFC 4180 and tested
against a real parser, because one unescaped comma in a note shifts every column
after it and silently corrupts somebody's analysis.

**CORS is open** on both files. Published data a browser cannot fetch is data
only a server can use, which excludes the people most likely to cite it. Both
carry `x-license` and a `Link: rel="license"` header.

**The landing page documents every field** — all 21 columns, the unit of each,
the closed set of method identifiers, a provenance row per provider, and an
explicit list of what the dataset does *not* contain (negotiated rates,
providers who publish nothing, history from before this site existed). Google's
guidance puts `Dataset` markup on the landing page, not the file, so that is
where it is: 4 JSON-LD blocks, Dataset among them, with both required properties
and eleven recommended ones including version-pinned `license`, open-ended
`temporalCoverage`, `variableMeasured` and two `DataDownload` distributions.

**`/data/` carries no ads**, enforced rather than merely omitted: `dataset` is a
new page type in `ALWAYS_AD_FREE`. An ad beside the dataset is worth a fraction
of a cent; being the source someone is willing to name is worth more.

**llms.txt now points at the file**, with the licence and the attribution line,
so an assistant has no reason to scrape a page instead.

**Three broken footer links, found and fixed.** The footer linked to
`/data/changelog/`, `/upi/limits/` and `/upi/rules/`. None of the three has ever
existed — every one was a 404 served to anything that followed it. The changelog
link now points at `/data/`; the two UPI links are gone until those pages do
exist. The check that would have caught them is below.

### Internal link check — `scripts/check-links.mjs`

Three footer links served a 404 from the day they were written, and 274
crawlability assertions did not notice. They could not: every one of them checks
what a page **contains**, and a broken link is a page containing exactly what it
should — an `<a href>`. Nothing was looking at the other end of it.

A dead internal link is worse than a missing page. It burns crawl budget, leaks
whatever authority the linking page had into nothing, and tells a reader who
trusted a navigation element that the site does not know its own shape. On a
site whose whole proposition is that the figures are checked, that is not
cosmetic.

`npm run check:links` crawls every URL in the sitemap and asserts six things:

| | Assertion | Why it is separate |
|---|---|---|
| 1 | Every sitemap URL returns 200 | A 404 in the sitemap is a page handed to Google that is not there |
| 2 | Every internal `href` returns 200 | The original defect |
| 3 | No internal link **redirects** | With `trailingSlash: true` a link to `/charges` answers 308 first. The fix is different — add the slash — so it is its own failure class |
| 4 | Every `#fragment` has a matching `id` | An anchor into a renamed heading lands the reader at the top of the page with no sign anything went wrong |
| 5 | No sitemap page is an orphan | A page nothing links to is one Google is asked to rank on a sitemap entry alone |
| 6 | Nothing linked is missing from the sitemap | The direction that actually bites: a page gets written and linked, the sitemap gating is forgotten, and it ships unsubmitted |

Current result: **71 targets, 69 fragments, 69 sitemap pages — all clean, no
orphans, no redirects.** The only linked paths absent from the sitemap are
`pricing.json` and `pricing.csv`, allowlisted because they are files, not pages:
no canonical, no title, nothing to rank.

**External links are never fetched**, deliberately. They would make a blocking
CI step depend on other people's uptime and rate limits, which turns it into a
coin flip. Source link rot is real, but it is a scheduled job's problem.

**Every one of the six was proven by watching it fail.** A guard nobody has seen
fail is not a guard. Restoring `/upi/limits/` in the footer produced the 404
failure; misspelling the skip-link target produced the fragment failure; a stub
server produced the redirect, orphan and unsubmitted-page failures.

Two things that cost real time, both worth knowing:

- **Next's `<Link>` silently normalises a slashless `href`.** Writing
  `href="/charges"` renders `/charges/`, so the redirect defect could not be
  reproduced through a component at all — hence the stub server. The assertion
  still earns its place: a raw `<a>`, or an href built from data, is not
  normalised.
- **A stale `next start` answered every assertion from the previous build.** It
  held port 3000, the new server failed to bind with `EADDRINUSE`, and all three
  checks passed against code that was no longer there. `pkill -f "next start"`
  does not end it, because the process renames itself `next-server`. Kill it by
  port. Noted in TECHNICAL.md §9, because it can make any of the three checks
  report a clean pass on a defect.

The first report was unreadable for a different reason: one misspelled
fragment in the root layout produced 69 identical failures, one per page, which
buried anything sitting underneath. Failures now group by **defect** rather than
by occurrence — one line, with a count and the first four places it appears.

**Client-boundary note:** the pricing barrel re-exports the seed repository,
which imports `node:fs`. Importing anything from it inside a `'use client'`
component dragged fs into the browser bundle and crashed Turbopack. Split out
`@/modules/pricing/client` — a pure types-and-constants entry with no node
imports — and allowed that one path in the ESLint boundary rule.

**Routing note:** `/charges/upi/` and `/charges/[gateway]/` collide. Resolved
with five thin static routes, since Next prefers a static segment over a
dynamic one. Verified: methods resolve to method pages, provider slugs still
resolve to provider pages, unknown slugs 404. There is a `check-ssr` assertion
on this, because a regression here would silently turn method pages into 404s.

## Phase 2.5 — launch fixes (done)

Deployed, mapped the domain, and fixed what that exposed.

- **Canonical origin mismatch.** Vercel serves `www`, the code declared the apex.
  All 58 sitemap URLs 308-redirected and every canonical pointed at a
  redirecting URL, so Google filed the whole site under "Page with redirect"
  and indexed nothing. Fixed by setting `NEXT_PUBLIC_SITE_URL` to the www
  origin. The build now warns when the canonical host and
  `VERCEL_PROJECT_PRODUCTION_URL` disagree.
- **robots.txt blocked our own OG image.** A blanket `Disallow: /*?` caught
  `/opengraph-image?<hash>`. Removed; there are no query-param surfaces here.
- **The localhost guard did not fire on Vercel.** It worked under `CI=1` but
  not `VERCEL_ENV`, because Turbopack does not expose arbitrary vars on
  `process.env` inside bundled code. Moved to `next.config.ts`.
- Vercel Web Analytics wired in (cookieless, same-origin, no CSP change).
- Favicon and a generated 1200x630 OG image added — neither existed.
- 4 titles over 60 chars and 10 descriptions over 155 trimmed.
- `.toLowerCase()` was rendering "mostly upi" in SERP titles.

## Phase 2 — comparisons (done)

- 28 `/compare/[a]-vs-[b]/` pages, one per pair.
- 6 `/best/[use-case]/` profiles.
- **Computed crossover verdicts.** Annual cost is linear in volume, so two
  providers' cost lines cross at most once; `findCrossover` bisects to the
  rupee. Three outcomes, all rendered honestly: `crosses`, `always`, `tie`.
- The `tie` case exists because Paytm and PhonePe publish identical rates. An
  alphabetical tie-break would have printed "Paytm is cheaper than PhonePe" —
  a fabricated difference. Guarded by a test.
- Gateway pages link to every comparison they appear in, generated from data.
